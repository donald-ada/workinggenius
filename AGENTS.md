# AGENTS.md

This file provides guidance to coding agents when working with code in this repository.

## What this repository is

The Working Genius workflow itself: a client-agnostic Agent Skills package — 24 skills under `skills/` and five subagents, each inside the skill that spawns it, all plain markdown folders any Agent Skills client can read. Nothing here is held back for one client. There is no runtime, no build and no test suite; what the skills claim is measured by an eval suite, `evals/` (below); the one script is the format's instrument, `skills/genius-file/measure.py`, which counts and never decides, and whose one writing command, `append`, writes only the log entry it is handed, where the caller named — a fork must be able to carry the whole thing as plain folders, and still can. Dogfood work files (`.genius/`) are gitignored and never shipped.

## Commands

There is nothing to build or run. Three checks matter when editing skills:

- **Count characters, never bytes.** `python3 skills/genius-file/measure.py count <file>` is the instrument and this one-liner is what it does; any number that enters a skill or a record comes from one of these and not from `wc -m` (which counts bytes under most non-interactive locales) or `awk length()`:
  ```
  python3 -c "import sys;print(len(open(sys.argv[1],encoding='utf-8').read()))" <file>
  ```
- **Relative links between skill files must resolve** (`agents/inventor.md`, `../tenacity/agents/reviewer.md`, `FILE-FORMAT.md`, `../genius-file/BACKLOG-FORMAT.md`; a work file's own links in a template, `log/…` and `CONTRACT.md`, are skipped). A one-off check:
  ```
  python3 -c "import re,os,glob;print([(f,t) for f in glob.glob('skills/**/*.md',recursive=True) for t in re.findall(r'\]\(([^)#]+)(?:#[^)]*)?\)',open(f,encoding='utf-8').read()) if not t.startswith('http') and '<' not in t and t!='CONTRACT.md' and not t.endswith('.log.md') and not t.startswith('log/') and '/log/' not in t and not os.path.exists(os.path.join(os.path.dirname(f),t))])"
  ```
- **Frontmatter must parse, and the instrument must not fail.** The frontmatter (a skill's `argument-hint` and `disable-model-invocation`, an agent's `name` and `description`) lives in YAML, and a stray indent drops the whole block without a word; four commands run `measure.py` before they read and a skill whose instrument fails would stall, so it exits 0 on an empty directory and on a malformed snapshot. One check for both:
  ```
  python3 -c "import yaml,glob;[yaml.safe_load(open(f,encoding='utf-8').read().split('\n---\n')[0][4:]) for f in glob.glob('skills/*/SKILL.md')+glob.glob('skills/*/agents/*.md')];print('frontmatter ok')" && python3 skills/genius-file/measure.py status >/dev/null && echo 'instrument ok'
  ```
- **The skills have an eval suite**, `evals/`, one case per claim the skills make that a fresh session can be caught breaking — an ordinary request never enters the flow (`no-hijack`), a question about work in flight is answered from the instrument and invents nothing (`nothing-in-flight`), an idea handed to the flow is interviewed and not built (`genius-starts-wonder`), discernment on a work with no paths runs Invention first (`discern-invents-first`, scaffolded), one slice is built red before green with its evidence in the log (`enable-red-before-green`, scaffolded), and a close-out whose log records a criterion as passed that fails on the code runs it fresh and does not mark the work done (`tenacity-reruns`, scaffolded). **The suite is written for Claude Code's `claude plugin eval` runner and this package no longer carries that client**: the cases, their graders and their scaffold scripts stay as the record of what was measured, and are not run here. Porting them to another client's runner is a separate piece of work. Each case is a prompt as a person would type it, graders that cost nothing and one judge rubric; results land in `evals/results/`, gitignored.

- **Release.** Any change under `skills/` that merges to `main` updates the version line in `README.md` in the same change. A skill added or removed moves the count in README's first line.

## Architecture

**One skill = one folder** `skills/<name>/SKILL.md`, frontmatter `name`, `description`, optional `argument-hint`. `disable-model-invocation: true` marks a command only the user types (`/genius`, `/architect`, `/designer`, `/compact`, `/distill`, `/reconcile`, `/triage`, `/waitwhat`, `/attack`, `/fresh-eyes`, `/setup-working-genius`); the six stage skills and the discipline skills (`genius-file`, `record-prose`, `errata`, `decision-record`, `domain-glossary`, `blindspot`, `diagnose`) are model-invoked. **The five subagents** — `skills/invent/agents/inventor.md` (spawned by the `invent` skill, inside `/discern` or `/invent` alone, one per angle), `skills/discern/agents/attacker.md` (by `/discern`, and by `/attack` outside the flow, one per path, blind to the others, because the session that read every path already prefers one), `skills/enable/agents/builder.md` (by `/enable`'s coordinator, one per slice), `skills/tenacity/agents/reviewer.md` (by `/enable` at a slice close, `/tenacity` at close-out, and `/fresh-eyes` outside the flow), `skills/designer/agents/design-critic.md` (by `/designer` on the tile the user chose) — are plain markdown briefs: frontmatter `name` and `description`, and no `tools` list, because where the client lets an agent inherit the session it should inherit everything, and a list only names less (the reviewer's read-only discipline is a rule in its body, not a grant). The body is the subagent's system prompt and carries the discipline; the spawning skill's task message carries the parameters (the problem and angle, the slice and where to build, the diff and what it is judged against). They live inside the skill that spawns them, not in a top-level `agents/`, so a skill, its task message and its agent's brief change in one folder. A client with a subagent registry loads them from its own agents directory (Command Code: `.commandcode/agents/` or `~/.commandcode/agents/`, giving each a `tools:` line, because there an agent with no `tools` gets none); a client without one still has the brief, which stands alone because it names the discipline skills it writes by, relative to itself, rather than relying on a preload. The skill names what the message must carry; the agent names what it hands back — one home each.

**Two things ride inside a skill folder besides the body.** First, the instrument: `/genius`, `/compact`, `/reconcile` and `/distill` run `measure.py` before they read — `status`, `snapshots`, `links`, `distill` — and a close runs `anchors` or `append` when it needs it; each names the script by a path relative to the skill's own folder, the standard way a skill points at a bundled file, so no client-named variable and no shell-injection directive are involved (injection is a client extension, not the standard's) and the same text works wherever the folder lands. Second, the discipline: each agent brief names the skills that own its rules (`genius-file`, `record-prose`, `decision-record`) by relative path, since there is no preload to expand. Both are read by the model, not executed by the client on the skill's behalf: the skill says which command to run, and the reader resolves the path.

**The flow** is five commands the user types in order — `/wonder → /discern → /galvanize → /enable → /tenacity` — with `/genius` as the map; `/discern` runs Invention first where no paths are on record, because nothing in Invention waits on the user (user ruling, 2026-09-25; `/invent` alone still explores without attacking). The flow never advances itself and never hijacks a request that didn't enter it; a stage the user doesn't type has no section in the work file, and that absence is the record.

**The work file is the whole handoff between sessions**, and its design is the part that takes several files to see. One piece of work = `.genius/<slug>/` holding three files with three growth laws: the snapshot `<slug>.md` grows by *scope* and has a 6000-character ceiling (Slices roster excluded); the log grows by *time*, is append-only and is a tree — a root `<slug>.log.md` with one line per branch, and one branch per stage, slice or contract version under `log/` — so appending or answering a question opens one branch and never the whole history; `CONTRACT.md` grows by *slice count* and holds the brief, seams, pinned values, each slice's acceptance criteria (their one home — the snapshot's slice line only links them) and the conventions the build established. Compaction routes each snapshot line by one question — *does this line still constrain work that isn't finished?* — under one invariant: nothing leaves the snapshot except into the log or `CONTRACT.md`, with a link left behind. Cross-work files at `.genius/` (`BACKLOG.md` + `BACKLOG.log.md`, `DECIDED.md`, `HISTORY.md`) have their own format. Where this is written: `genius-file/FILE-FORMAT.md` (the shape), `genius-file/BACKLOG-FORMAT.md`, `genius-file/FORMAT-EDGES.md` (the measurements behind the rules, with commit hashes).

**Two layers run through every file the flow writes**: what *binds* (snapshot, contract, `DECIDED.md`, `CONTEXT.md`, backlog seeds) is rewritten in place when wrong; what *records* (any log, any done file) is appended to and never edited. `errata` owns that rule; `/reconcile` sweeps drift against the repo; `/compact` and `/distill` are the retroactive passes. There is one format, and no recognition of older ones: a file in another shape is read for what it holds and brought to the format when next written to.

**Each rule has exactly one home**, and other skills point at it rather than restate it — the compaction question and its destinations in FILE-FORMAT, the sentence discipline in `record-prose`, the correction moves in `errata`, the seed shape in BACKLOG-FORMAT. When editing, change the owning file and check the pointers; a rule copied into a second skill drifts the first time either is edited.

## How skills are written

- Concept first: each skill carries its purpose, its failure mode, the concept in one bold line, and one threshold that must be honestly true before the next stage. Stage skills also carry a short `## How it runs` list. Every rule states its why in the same sentence; a constraint that can't name its reason doesn't land.
- Action constraints are where the measured value lives and stay firm (interview is live dialogue, red before green, fresh verification, wounds found never manufactured, findings carry evidence). Taxonomies are floors, not scripts.
- Killed designs stay killed unless measured evidence reopens them. Before proposing express paths, sizing calls, autonomy modes, gate checklists in work files, or scripts that parse a work file's prose or decide anything, read the git history — `0cc21de`, `925accf`, `275ed4f`, `f8897e9` each record a ruling and its kill-reason. Reopening one costs a counter-example somebody measured, named against the leg it breaks.
- Commit messages carry the reasoning — what was observed, what changed, why — because the repo has no other record of its rulings.
