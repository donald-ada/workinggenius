# Enablement

The genius of doing the work the work needs. Its failure mode is flying blind: code produced without feedback until a big-bang reveal at the end.

The concept: **build one slice at a time, in a fresh context, with reality voting every few minutes.** Tests lead the code — write the failing test at the agreed seam and watch it fail before the implementation exists; this is the one discipline a capable model still talks itself out of (measured 0/3 baseline), so hold it even when momentum says skip it. Test behavior through public seams, not implementation. Some criteria can't be red-green — verify those against the real thing and record what you observed; the rule is feedback, not ceremony.

Coordinating multiple slices? Hand each builder the work file path, verify each returned slice against real output yourself, and stay awake until they're done — a builder's word is not evidence. When the plan meets reality and loses, surface the problem and record the change — never silently improvise; a decision made without the user is an `assumed:` line, flagged for review. Close each slice in **one commit**: the code, its evidence, the `.genius/` updates — work file and record alike — where `.genius/` is committed, and the close of its issue if it carries one. The record then updates as a side effect of the action you had to take anyway, rather than as bookkeeping anyone has to remember. (An issue closes via `closes #N` in the message where that commit lands on the default branch, and directly, pointing at the commit, where it won't.) **Closing a slice writes its record** — its entry in the work's enablement record, naming per criterion what ran and what it showed, written while the output is still on screen; the closing commit carries it where `.genius/` is committed, and where `.genius/` is gitignored the entry is written at that same moment all the same. Put it in the record and not in the commit message — the work-file discipline (the `genius-file` skill) names why a message can't serve as the record. What the work file itself takes is only what a later session must stand on, and each piece goes where its reader already looks: the slice's line in the plan marked done and linked to that entry; a convention introduced or a pinned value revised — a number, a seam, a criterion — written into the plan's contract beside the seams and pins it already carries, because that is what the next slice reads, and where the build disproved something already written there, corrected under the `errata` skill's rule: the contract rewritten, the record that carried the wrong line appended to with what overturned it; and the carry-forward the close-out must consume, the `assumed:` lines and the edges left untested. Whoever makes the commit makes the correction, in that slice's issue too where it carries one. Start each slice by reading the plan's slice list, so a slice that closed without marking itself is caught by the next slice rather than at close-out. A slice reshaped mid-build closes its old issue with the reason, and its replacement joins the work's parent issue and label like any other.

Then `/tenacity`. Done when every slice is built and every criterion checked against output that actually ran — its record entry naming, per criterion, what ran and what it showed. A criterion checked in your head has not been checked.
